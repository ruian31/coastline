# 手机性能与默认横屏全屏

2026-10-21。用户使用一加12 Chrome，首轮反馈为可进入但画面掉帧；随后要求手机默认横屏全屏。

## 已实现

- 小地图预计算路线Path2D和地标位置，避免每次重绘重复计算约350个曲线样本。
- 图标、车载电台与状态文案只在变化时改DOM，保留速度、行程和地图实时更新。
- 手机自动档从流畅档启动，DPR1，减少远景草丛、灌木和蕨类实例，关闭实时阴影并使用轻量车底接触影。近景风动、车身、HDR反射保留；设置中仍可提高画质。
- 手机取消触控面板等处的实时背景模糊，降低合成负担。
- 默认竖屏入口显示横置引导；点击开始的同一次用户手势先申请全屏，再尝试锁定landscape。横置后界面铺满可用画面，也保留临时竖屏入口。
- 添加web manifest（fullscreen/standalone、landscape）和iOS主屏幕元数据。不支持API时提供手动横置和添加到主屏幕说明。
- 手机稳定生产预览：`http://192.168.3.10:5190/`；开发5188仍用于工程调试，不推荐用热更新过程判断帧稳定性。

## 对照测量

相同路线、844×390 Android视口、桌面RTX4050、4倍CPU节流，8秒采样。以下为优化方向的对照，不能换算成一加12帧率。

| 指标 | 原中档 | 缓存UI/地图中档 | 新流畅档 |
| --- | ---: | ---: | ---: |
| DOM变更 | 1543 | 14 | 14 |
| 子节点变更 | 1152 | 7 | 7 |
| 布局耗时 | 108ms | 3ms | 2ms |
| 脚本耗时 | 2036ms | 1752ms | 1647ms |
| 主线程任务耗时 | 2689ms | 2111ms | 1995ms |
| DPR | 1.15 | 1.15 | 1 |

新流畅档的任务总耗时下降约25.8%，像素负担下降约24.3%；此处没有以桌面GPU的60fps声称手机60fps。命令：`node scripts/profile-mobile.mjs <label> <medium|low>`，原始JSON在 `artifacts/mobile-performance/`。

## 真机反馈与回归

用户用同一一加12 Chrome复测生产地址后明确反馈：**“明显更流畅，横屏全屏正常”**。这是本次Android真机体验验收的直接证据；iPhone真机仍待验证。

桌面5项、Android7项、WebKit7项功能检查通过（横屏默认与API调用顺序两项只对手机执行）。全屏顺序测试使用能力桩验证调用顺序，不能据此宣称iPhone原生能力支持。其余实际操作覆盖三车加速、三镜头、巡航接管、触控、菜单、横竖屏、暂停声音、车内急转与慢资源加载。

## 2026-10-23 · 公路外视野与实例筛选

自由驾驶暴露整片地图的实例批次浪费。现在按每个草丛、岩石、树木和扫描灌木的实际包围球筛选，保持稳定的原始位置、颜色与风动相位；只有实例顺序变化时上传矩阵。树冠增加远景几何，手机130米/桌面200米附近带24米回差切换，近景保持原细节。已有投影对象保留镜头外投影范围。多个树群绘制批次合并，纹理数量没有增加。

- 生产回归30通过、3项平台跳过；最终扫描灌木筛选补充8项通过、1跳过。树根检查覆盖全部原始摆放，并校验实际可见实例的完整变换。
- 实际键盘/Android双指沿山坡到岩壁后方、停车旋转镜头、再回路成功，无脚本错误。手机再次点击“追随”可回正镜头，桌面使用回正按钮。
- 先前公路外过程峰值桌面760982三角形/149调用、手机360264/148；优化后过程桌面593187/111，手机304475/112，手机仍比300k目标高约1.5%。两次实际输入过程存在轨迹与镜头差异，不能当成逐帧同轨迹基准或真机帧率。
- 同一固定手机横屏rock-side机位344310→286856三角形、129→102调用（加入最后的扫描灌木筛选前）。12个正式桌面/手机机位均在既定预算内，纹理仍39张。活跃驾驶画面对照RGB差值大于3的像素约0.05%，桌面车身近景区域逐像素相同；变化集中于远景树冠。
- 4倍CPU节流、8秒默认低档：巡航Task2127ms/Script1798ms；最终手动Task2337ms/Script1950ms。较之前手动2224/1834ms约高5%/6%，采样与路线差异会影响结果；不能把三角形减少等同于真机帧率提高。
- `artifacts/evidence-visible-instances.json`对应最终12机位与20项文件验证。原始绕行、失败的触控脚本（尝试点击手机隐藏的桌面回正按钮）、修复后的触控路径与各轮测量均保留，未覆盖先前基线。下一阶段做R16海水进退，并复核真实手机GPU表现。

## 平台边界与来源

[MDN ScreenOrientation.lock](https://developer.mozilla.org/en-US/docs/Web/API/ScreenOrientation/lock)说明方向锁定通常限于移动设备和全屏上下文；[MDN requestFullscreen](https://developer.mozilla.org/en-US/docs/Web/API/Element/requestFullscreen)说明全屏需用户激活。故网页载入时不反复发出无效请求，而在开始点击中申请。

[WebKit iOS Fullscreen追踪](https://bugs.webkit.org/show_bug.cgi?id=206854)及[iPhone非视频元素全屏](https://bugs.webkit.org/show_bug.cgi?id=212934)记录iPhone的能力限制。产品以能力检测与主屏幕模式补充，不能承诺网页可以强制覆盖所有Safari/系统方向设置。
